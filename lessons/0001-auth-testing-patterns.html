Lesson 0001: Mocking Auth Sessions in Vitest

Understanding vi.mocked, Better Auth session guards, and Option A vs Option B design tradeoffs

Mission Context

You are designing test suites for server actions across multiple domain modules (goals.test.ts, transactions.test.ts, friends.test.ts, and groups.test.ts). To test these actions cleanly, you need to understand how session verification works and how Vitest mocks it.

Concept 1: What is Session Mocking & Why Do We Need It?

In Next.js server actions, your backend checks who is making the request using Better Auth:

// Example inside a Server Action
const session = await auth.api.getSession({ headers: await headers() });
if (!session) {
  throw new Error("Unauthorized");
}
// Proceed with business logic...

During automated unit tests, running a real auth flow (hitting PostgreSQL or cookie parsers) is slow and complex. Instead, we mock auth.api.getSession so that it returns a fake session object when we want an authenticated user, or null when testing an unauthenticated user.

Concept 2: What is vi.mocked()?

Vitest replaces your real module with a mock object via vi.mock("@/lib/auth"). However, TypeScript still thinks auth.api.getSession is a standard function, not a mock!

vi.mocked(auth.api.getSession) does not change any runtime code—it simply tells TypeScript: "Treat this function as a Vitest mock so I can call .mockResolvedValue() or .mockReturnValue() safely with full autocompletion."

Concept 3: Option A vs Option B Tradeoff Analysis

Option A: Direct vi.mocked calls inside test setup/files

Code Example:

vi.mocked(auth.api.getSession).mockResolvedValue({
  user: { id: "user-1", email: "user@example.com" },
  session: { id: "sess-1", userId: "user-1", expiresAt: new Date() }
} as any);
  • Pros: Zero extra abstraction files. Explicit per-test visibility.
  • Cons: High repetition (duplicating session shapes across 4+ test files). If Better Auth session schema changes, every single test file needs manual updating.

Option B (Recommended for standard suites): Shared Test Helper Function

Code Example:

// In a shared utility like src/test/utils.ts
export function mockSession(user: { id: string; email?: string } | null = { id: "user-1" }) {
  if (!user) {
    vi.mocked(auth.api.getSession).mockResolvedValue(null);
    return;
  }
  vi.mocked(auth.api.getSession).mockResolvedValue({
    user: { id: user.id, email: user.email ?? `${user.id}@example.com` },
    session: { id: `sess-${user.id}`, userId: user.id, expiresAt: new Date() },
  } as any);
}
  • Pros: DRY (Don't Repeat Yourself). One-line calls in tests (mockSession({ id: "u1" }) or mockSession(null)). Single source of truth if session fields change.
  • Cons: Requires setting up a shared helper module (e.g. src/test/utils.ts).

Recommendation for Ledgerflow

Option B with Option A fallbacks is the industry gold standard:

  1. Create a helper mockSession(user) in a shared test utility.
  2. Use mockSession() in beforeEach across goals.test.ts, transactions.test.ts, friends.test.ts, and groups.test.ts.
  3. Reach for direct vi.mocked(...) only when a test requires unique, non-standard session properties.
